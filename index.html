HOW IT WORKS

Your agent leads.
Another agent lends a hand.

The orchestrator is the agent you’re working with.
The subagent runs the task it receives in its own harness.

  1. 01

    Choose who can help.

    Pick a task, a subagent, and its model. Keep the tools, accounts, and provider settings you’ve already configured.

  2. 02

    Apply your rule.

    Bridge connects supported agents and gives them the rule. First-time setup may need a reload or hook approval.

  3. 03

    Keep working.

    Your orchestrator sends the task and context. The subagent works in the same project folder, then returns its result.

Independent work can continue in the background. Follow up with the same subagent while its session is alive. How results come back ↗

THE DETAILS

Before you begin.

Which account pays for the model?+

The subagent uses its harness’s existing account, API key, or provider. Subscription allowances and API charges follow that setup. Bridge does not provide model access or sell another subscription.

What stays on my computer?+

Bridge’s rules and coordination run locally. Your agents still send prompts and code to their configured model providers. A shared project folder does not copy the whole chat: the orchestrator supplies the context each task needs.

How do results and follow-ups work?+

Supported integrations return results to the session that started the task. Codex hooks deliver during active turns or when a turn stops; an idle chat receives pending results next turn. Follow-ups reuse the same worker conversation while its process is alive. Restarting the harness ends that continuity.

What do “can use” and “should use” mean?+

“Can use” lets the orchestrator decide whether to delegate. “Should use” instructs it to delegate matching tasks; it cannot guarantee a model will obey. Multiple agents or models are alternatives: the orchestrator picks one of each per task. Bridge enforces those allowed choices when a task runs.
